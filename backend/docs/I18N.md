# Internationalisation (I18N-01) — guide développeur

Langues prises en charge : **fr** (source et langue par défaut) et **en**.
Le cahier des charges (CDC-INVENTAIRE, I18N-01) cite aussi **pt** : non livré, voir « Ajouter une langue ».

## 1. Stratégie commune aux trois parties

| Partie | Où sont les textes | Langue choisie par |
|---|---|---|
| Web (`apps/web`) | `src/i18n/fr.ts`, `en.ts` (+ `ui.fr.ts`, `ui.en.ts`) | choix de l'utilisateur, sinon langue du navigateur |
| Mobile (`apps/Mobile`) | mêmes fichiers, **mêmes clés** que le web | choix de l'utilisateur, sinon langue de l'appareil |
| Backend | messages français dans le code + `src/shared/i18n/messages.en.js` | `Accept-Language` (requête) ; `Profile.locale` (notifications, e-mails) |

- Un même texte porte **la même clé** sur le web et le mobile (`ui.<clé>`). `scripts/i18n/check-i18n.mjs` vérifie que les clés communes ont le même texte et la même traduction.
- Les clients envoient `Accept-Language` à chaque appel. Ils reportent la langue choisie sur le profil (`PATCH /me { locale }`), ce qui permet au serveur d'écrire les notifications dans cette langue.
- Les champs machine ne sont **jamais** traduits : `code`, `errors[].field`, `errors[].code`, valeurs d'énumération.

## 2. Backend

### Fonctionnement

- `localeMiddleware` (posé dans `app.js`) lit `Accept-Language`. Il fixe `req.locale`, l'en-tête `Content-Language` et un contexte asynchrone.
- `errorHandler` traduit `message`. Pour les erreurs par champ, il **ajoute** `errors[].message` (`code` inchangé).
- `validate` produit `errors[].message`. Les messages Zod par défaut (« Required », « Invalid email »…) sont régénérés dans la langue de la requête.
- `success()` traduit le message de succès.
- `notify()` traduit titre et corps dans la langue du **destinataire** (`Profile.locale`).
- Les libellés d'alertes et de plages agronomiques sont traduits à la sortie.
- Les deux e-mails applicatifs (contact d'une exploitation, décision de vérification) sont rédigés dans la langue du destinataire.

### Écrire un message

Écrire le message **en français** dans le code, comme avant :

```js
throw ApiError.notFound('Parcelle introuvable');
throw ApiError.badRequest(`Transition interdite : ${from} → ${to}`);
```

Puis ajouter sa traduction dans `src/shared/i18n/messages.en.js` :

```js
['Parcelle introuvable', 'Plot not found'],
['Transition interdite : {status} → {status2}', 'Forbidden transition: {status} → {status2}', ['status', 'status2']],
```

Pour un gabarit, chaque segment variable devient `{nom}` et est listé en 3ᵉ position. Les valeurs capturées sont réinjectées et sont elles-mêmes traduites si elles figurent au catalogue.

Un message absent du catalogue reste en français. Ce n'est jamais une erreur bloquante, mais `node scripts/i18n/check-i18n.mjs` et `tests/i18n.test.mjs` doivent rester au vert.

### Ajouter une langue (ex. pt)

1. Backend :
   - créer `messages.pt.js` ;
   - ajouter `pt` à `SUPPORTED_LOCALES` et au catalogue dans `shared/i18n/index.js` ;
   - ajouter un bloc `pt` dans `ZOD_DEFAULTS` ;
   - étendre l'énumération `locale` de `users.schema.js`.
2. Web et mobile :
   - ajouter `pt` au type `Locale` (`lib/format.ts`) et à `BCP` ;
   - créer `pt.ts` et `ui.pt.ts`, typés `Dictionary` / `UiDictionary` : la parité est alors imposée à la compilation ;
   - compléter `SUPPORTED_LOCALES` et `detectDeviceLocale`.

## 3. Limites connues

- **SMS d'alerte :** ils restent en français. Leur texte est construit sous contraintes GSM-7 et de longueur (`alerts.service.js`), et les paramètres agronomiques y sont abrégés. Une version anglaise demande des gabarits dédiés et testés en longueur.
- **E-mails d'authentification :** confirmation, réinitialisation et lien magique sont envoyés par Supabase Auth. Leurs gabarits se configurent dans la console Supabase, hors du code.
- **Libellés calculés et stockés :** les libellés écrits par le moteur de recommandation dans des résultats persistés restent dans la langue de calcul (français).
